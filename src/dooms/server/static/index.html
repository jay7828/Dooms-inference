How a sentence becomes motion

Four narrow agents, each doing one job, hand off to a controller stack that runs at control rate. Nothing is a single giant prompt.

01
Scout

Looks at the scene, notes what state each object is in (upright, fallen, blocked) and splits the task into ordered subtasks, or says plainly that the task cannot be done.

02
Composer

For each subtask, reuses a stored skill or writes a new recipe from five controller types, naming the keypoints it needs.

03
Tuner

Chooses the numbers: heights, force limits, widths, with the values that worked before offered as hints.

04
Spotter

Finds each keypoint in the image, refines it with a zoomed look, and lifts it to 3D with depth and a fitted surface normal.

What we have learned

The pieces of this project that are research rather than plumbing.

Task-axis control

Behaviour is expressed as aligning axes between keypoints (position, axis, yaw, force, gripper), stacked by priority with exact null-space projection, instead of free-form joint trajectories.

Coarse-to-fine grounding

A grasp needs the target to about 5 mm. Pointing, a zoom pass, depth lift, then a wrist-camera close-up before reaching. Failures first try re-looking; only then a full replan.

A skill library that grows

Successful recipes are stored with roles instead of object names and reused later, along with the parameters that worked. Each arm keeps its own library.

Reasoning about obstacles

A depth-based clearance check tells the planner when open fingers would hit a neighbour, and it can decide to push the box aside before the original task.

Typed decision advisor

Two small calls, "did the subtask succeed" and "which recovery", can be answered by a typed-decision model with a confidence, falling back to rules when unsure.

Inference in the browser

The whole stack was ported to TypeScript and a web worker. Claude is called straight from the page with the visitor's own AWS credentials; skills live in IndexedDB.
